운영 흐름도 — 어드민으로 Pixengo를 운영하는 방법

고객(게스트 · 호스트 · 드라이버)이 편하려면 운영자가 먼저 움직여야 합니다. 덱 5장대로 미배차는 사후 수습이 안 되므로 운영의 중심은 도착 전입니다. 호스트는 돈과 게스트 개인정보에 닿지 않고, 기사는 바뀐 사항을 묻기 전에 먼저 받습니다.

결정 기한[결정 기한] — 운영 결정 O-01~O-12은 Phase 0 운영 시작 전

원본: 비공개 저장소의 docs/admin-ops-process.md (프로세스 카드 P-01~P-13 · 운영 결정 O-01~O-12). 상태 전이와 금전 판단의 원본은 상태별 조치표와 운영 설계 문서입니다. 설계안이며 [대괄호] 값은 덱에 없는 미정 수치입니다.

확정된 흐름운영자 업무정책 결정(D-nn) 전 — 실행 비활성도착 전 구간

1. 운영 구조 — 누가 어디로 들어와 누가 처리하나

Phase 0에는 어드민만 있습니다(덱 9장). 게스트 웹 · 호스트 폼 · 드라이버 앱이 없는 동안에는 채널톡 · 전화로 받은 내용을 운영자가 대신 입력하고, 입력 출처를 이력에 남깁니다.

2. 콜 한 건의 운영 흐름

예약부터 주간 정산까지 열 단계. 가운데 굵은 줄이 운영자 업무이고, 금색 테두리 구간(배정 ~ 비행 중)이 미배차를 막는 시간입니다. 단계 머리글을 누르면 아래 설명으로 이동합니다.

먼저 알아 둘 말

콜카드
예약 1건의 기록입니다. 예약부터 정산까지 같은 기록 하나가 상태만 바뀝니다.
웹훅
PG(결제 대행사)가 결제 결과를 Pixengo 서버로 자동 통보하는 것입니다. 사람에게 가는 안내가 아니며, 결제 확정의 유일한 기준입니다.
대행등록
운영자가 고객 대신 예약을 입력하는 것입니다. 입력한 사람이 이력에 남습니다.
강제배차
기사 앱 수락을 기다리지 않고 운영자가 기사를 직접 정하는 것입니다. 기사에게 먼저 연락해 수락을 받은 뒤 배정합니다.
미배차 위험
도착이 가까운데(도착 [3]시간 전) 아직 기사가 없는 콜에 붙는 표시입니다. 상태가 아니라 관제 화면의 경고입니다.
노쇼 신청
게스트가 나타나지 않을 때 기사가 올리는 신청입니다. 운영자가 확인하기 전에는 노쇼가 아닙니다.
자동결제 토큰 · QR
토큰은 예약금 결제 때 받아 두는 잔액 자동 청구 권한입니다. 토큰이 없으면 기사 앱에 결제용 QR을 띄웁니다.
D-nn · O-nn
아직 정하지 않은 규칙입니다. D는 돈·종료·제재 정책, O는 운영 방식입니다. 걸린 버튼은 시안에서 비활성입니다.
1

예약

P-0103 새 예약 · Sheet · 02 콜카드 · 큐 + 상세

여행객의 공항 픽업 예약을 받아 콜카드를 만들고, 예약금을 낼 결제링크를 보냅니다.

누가 누구에게

  • 게스트 → 운영자채널톡(중국어)으로 날짜 · 편명 · 인원 · 목적지를 보내 예약을 요청합니다. 호스트(게스트하우스 · 호텔)가 손님 대신 요청하기도 합니다. Phase 1부터는 게스트 웹 · 호스트 간이 폼으로 직접 입력합니다.
  • 운영자 → 도착편 API편명으로 도착 터미널(T1 · T2)과 도착 예정 시각을 조회합니다.
  • 운영자 → 게스트게스트가 직접 요청했으면 채널톡으로 결제링크를 보냅니다.
  • 운영자 → 호스트호스트가 요청했으면 알림톡으로 결제링크를 보내고, 호스트가 손님에게 전달합니다. 호스트는 결제하지 않고 손님 개인정보도 입력하지 않습니다. 이름 · 연락처는 게스트가 결제 페이지에서 직접 넣습니다.

운영자가 하는 일

  1. 편명 조회 — 며칠 앞 예약이라 조회되지 않으면 편명 · 예정 시각을 받아 적고 '도착 확인 필요'로 둡니다.
  2. 목적지 검색 — 자체 호텔DB → 네이버 → 구글 순서로 찾습니다.
  3. 인원 · 캐리어로 차량에 들어가는지 확인합니다.
  4. 견적 확인 — 운임 + 서비스료(5,000원 + 5%), 지금 낼 예약금 30%.
  5. '생성 · 링크 발송'을 누릅니다. 요율은 이 순간 값으로 콜카드에 복사돼, 나중에 요금정책이 바뀌어도 이 예약은 그대로입니다.

끝나면 콜카드가 결제대기 상태로 생기고, 링크를 어느 채널로 언제 보냈는지 기록됩니다.

결정 대기 링크 유효 시간 · 예약금 반올림(O-07) · 조회 안 되는 편명 처리(O-11) · 알림톡 승인 전 발송 경로(O-05)

2

예약금 결제

P-0202 콜카드 · 큐 + 상세 · 01 관제 · 도착 타임라인 + 배정

게스트가 링크에서 예약금 30%를 내면 결제가 확정되고, 콜이 기사 배정 단계로 넘어갑니다.

누가 누구에게

  • 게스트 → PG결제 페이지에서 AlipayCN · 해외카드로 예약금을 냅니다.
  • PG → Pixengo 서버웹훅으로 결제 결과를 자동 통보합니다. 운영자가 누구에게 보내는 안내가 아닙니다. 같은 거래번호(pg_tid)로 두 번 와도 한 번만 반영됩니다.
  • 시스템 → 게스트결제가 확정되면 예약 확정 안내가 나갑니다(안내 문구 · 채널은 O-05).
  • 운영자 → 게스트링크가 곧 만료되는데 아직 안 냈으면 채널톡 · 알림톡으로 결제를 다시 안내합니다([n]회, O-08).

운영자가 하는 일

  1. 관제 화면 '결제대기' 필터로 아직 안 낸 콜을 봅니다.
  2. 게스트가 '결제했어요' 캡처를 보내도 웹훅이 오기 전에는 확정이 아닙니다. PG 거래를 조회해 확인하고 게스트에게는 '확인 중'이라고 답합니다.
  3. 만료되면 콜은 '링크 만료'로 끝납니다. 게스트가 원하면 링크를 다시 만듭니다.

끝나면 웹훅으로 결제가 확정돼 배차대기로 넘어가거나, 링크 만료로 끝납니다.

결정 대기 재안내 시점 · 횟수, 링크 재생성 방식(O-08)

3

배정

P-0301 관제 · 도착 타임라인 + 배정 · 11 관제 · 기사 반납 → 재배정 · 16 설정 · 거점 운영값

결제된 콜에 기사를 정합니다. 기사가 앱에서 직접 수락하는 것이 기본이고, 안 잡히거나 Phase 0이면 운영자가 정합니다(강제배차).

누가 누구에게

  • 시스템 → 기사들Phase 1: 기사 앱에 콜이 공개되고, 원하는 기사가 수락합니다.
  • 운영자 → 기사강제배차 전에 전화 · 메신저로 '이 날 이 시각 이 콜 가능하세요?'라고 먼저 묻고 수락을 받습니다. 동의 없이 배정하지 않습니다.
  • 시스템 → 기사배정이 확정되면 기사에게 배정 알림이 갑니다. Phase 0(앱 없음)에는 운영자가 직접 전달합니다.
  • 시스템 → 게스트기사 · 차량 · 픽업 위치 안내가 나갑니다. 운영자는 실제로 전달됐는지 확인합니다.

운영자가 하는 일

  1. 관제 화면 오른쪽 배정 패널에서 후보 기사를 봅니다. 추천 순서는 참고용입니다.
  2. 화면이 기사 승인 여부 · 차량에 인원과 짐이 들어가는지 · 다른 콜과 시간이 겹치는지를 검사합니다.
  3. 기사 수락을 받은 뒤 배정하고 배정 사유를 적습니다.
  4. 배정된 기사가 나중에 반납하면 같은 콜카드가 배차대기로 돌아오고, 이 단계를 다시 합니다.

끝나면 배차완료 상태가 되고 게스트에게 기사 안내가 전달됩니다.

결정 대기 반납 페널티(D-12) · 끝내 기사를 못 구했을 때 미배차 확정 · 환불(D-08a)

T-[24]h 점검

P-0401 관제 · 도착 타임라인 + 배정 · 08 관제 · 시각 변경 · 대기

도착 하루 전쯤 콜마다 문제가 없는지 훑어봅니다. 게스트가 비행기에 타면 연락이 안 되므로 그 전에 확인해야 합니다.

누가 누구에게

  • 운영자 → 게스트안내 채널(채널톡 등)이 끊겨 있으면 게스트가 등록한 다른 연락 경로로 픽업 안내를 다시 보냅니다. 호스트에게 알린 것은 게스트에게 전달된 것으로 치지 않습니다.
  • 운영자 → 기사다음 날 콜 일정을 확인합니다(제안 — 확인 방식은 O-09).

운영자가 하는 일

  1. 점검 세 가지: 결제가 끝났나 · 기사가 정해졌나 · 게스트에게 안내가 닿는 채널이 살아 있나.
  2. 결제가 안 됐으면 2단계, 기사가 없으면 3단계로 돌아갑니다.
  3. 연락이 닿지 않으면 '연락 실패' 작업으로 올려 담당자와 마감을 정합니다.

끝나면 점검 기록이 남고, 걸린 문제는 담당자가 있는 작업으로 넘어갑니다.

결정 대기 점검 시점 [24]시간(O-09)

T-[3]h · 비행 중

P-04 · P-0501 관제 · 도착 타임라인 + 배정 · 08 관제 · 시각 변경 · 대기 · 11 관제 · 기사 반납 → 재배정

도착 몇 시간 전까지 기사가 없는 콜(미배차 위험)을 없애고, 도착 시각이 바뀌면 기사에게 먼저 알립니다. 이 구간을 놓치면 게스트는 공항에 발이 묶입니다.

누가 누구에게

  • 도착편 API → 시스템비행기 도착 예상 시각이 바뀌면 자동으로 감지해 관제 화면 '시각 변경'에 올립니다.
  • 운영자 → 기사새 도착 시각과 픽업 목표를 알리고 확인을 받습니다. 새 시각에 못 오면 다시 배정합니다.
  • 운영자 → 게스트바뀐 내용을 보내 둡니다. 비행 중이면 읽지 못하므로, 착륙 후 확인할 수 있게 남겨 둡니다.

운영자가 하는 일

  1. 미배차 위험 해소: 관제 화면 '미배차 위험' 필터를 엽니다(도착 [3]시간 전인데 기사 없는 콜, 빨간 테두리).
  2. 배정 패널의 후보 기사에게 차례로 전화해 수락을 받고 강제배차합니다.
  3. 아무도 안 되면 시도 기록을 남기고 계속 찾습니다. '미배차 확정(전액 환불)'은 정책 결정 전(D-08a)이라 버튼이 비활성입니다. 포기로 끝내지 않습니다.
  4. 시각 변경: 기사 확인을 받은 뒤 '변경 확인'을 눌러 표시를 해제합니다.

끝나면 도착 전에 모든 콜에 기사가 있고, 바뀐 시각을 기사가 알고 있습니다.

결정 대기 미배차 위험 기준 [3]시간(O-09) · 재안내 기준 [분] · 미배차 확정(D-08a)

착륙 · 픽업

P-0608 관제 · 시각 변경 · 대기 · 09 관제 · 노쇼 확인

비행기가 내렸는지, 기사가 약속 장소에 있는지, 게스트가 나오는지 확인합니다.

누가 누구에게

  • 도착편 API → 시스템착륙 정보가 들어옵니다. API가 [15]분 넘게 응답이 없으면 관제 화면 '도착 확인'에 올라오고, 운영자가 공항 운항 정보 등으로 직접 확인해 근거를 적습니다.
  • 기사 → 시스템공항 도착을 보고합니다(기사 앱, Phase 0은 운영자에게 전화). 콜이 픽업대기가 됩니다.
  • 운영자 → 게스트게스트가 안 보이면 연락을 시도하고 시각 · 채널 · 결과를 기록합니다.
  • 기사 → 운영자오래 기다려도 게스트가 안 나오면 '노쇼 신청'을 올립니다.
노쇼 신청 검토란 기사 신청만으로 노쇼가 되지 않습니다. 운영자가 네 가지를 확인합니다. ① 비행기가 실제로 착륙했나 ② 기사가 픽업 장소에 도착했나 ③ 무료 대기 시간이 지났나 ④ 게스트에게 연락을 시도했나. 넷 다 확인돼야 노쇼로 확정하고, 확정되면 예약금은 돌려주지 않고 70/30으로 나눕니다. 지금은 대기 시간 · 연락 횟수 · 배분 기준이 정해지지 않아 확정 버튼이 비활성입니다. 그동안 운영자는 기사에게 대기 유지 같은 지시를 하고 판단 메모를 남깁니다. API 장애로 착륙을 모르면 노쇼로 판단하지 않습니다.

끝나면 게스트가 타면 탑승 상태가 되고 운행 시작 시각(start_trip_at)이 기록됩니다.

결정 대기 무료 대기 기준(D-01) · 연락 횟수(D-02) · 70/30 배분(D-03) · 대기 연장(D-11)

운행

01 관제 · 도착 타임라인 + 배정 · 02 콜카드 · 큐 + 상세

게스트가 타면 운행이 시작되고, 이때부터는 취소할 수 없습니다.

누가 누구에게

  • 게스트 · 기사 → 운영자운행 중 문의나 문제는 채널톡 · 전화로 들어옵니다.
  • 운영자 → 기사하차 예상 시각이 한참 지나도 확정총액이 들어오지 않으면 기사에게 연락합니다(제안 — 기준은 O-12).
운행 모니터링은 어떻게 MVP에는 실시간 위치 추적이 없습니다. 덱 9장에서 위치추적은 Phase 4의 별개 시스템입니다. 운영자가 보는 것은 상태와 시간입니다. 탑승 시각과 네이버 경로 기준 예상 소요를 보고, 문의에 답하고, 너무 오래 끝나지 않는 운행만 확인합니다. 운행 중 취소 요청에는 취소할 수 없다고 안내하고, 요금 이의는 운행 후 검수로 받습니다.

끝나면 기사가 하차 직전 확정총액을 입력하면 잔액결제대기로 넘어갑니다.

결정 대기 운행 중 이상 판단 기준(O-12)

잔액 결제

하차 직전 확정된 요금에서 예약금을 뺀 잔액을 받습니다.

누가 누구에게

  • 기사 → 시스템하차 직전 기사 앱에 확정총액을 입력합니다. 잔액 = 확정총액 − 예약금.
  • 시스템 → PG예약금 때 받은 자동결제 토큰이 있으면 서버가 잔액을 자동 청구합니다. 게스트는 아무것도 하지 않습니다.
  • 기사 → 게스트토큰이 없으면 기사 앱에 QR을 띄우고, 게스트가 휴대폰으로 스캔해 결제합니다.
  • PG → Pixengo 서버웹훅으로 결제가 확정됩니다. 기사가 '결제됐어요'라고 알려도 그것만으로 확정하지 않습니다.
  • 운영자 → 게스트QR이 안 되면 대체 결제링크를 보냅니다.

운영자가 하는 일

  1. 관제 화면 '잔액 청구' 필터에서 오래 걸리는 콜을 봅니다.
  2. 기사에게 QR을 다시 띄우도록 요청하거나 게스트에게 대체 링크를 보냅니다. 모든 시도는 같은 잔액 청구 한 건에 묶입니다.
  3. 끝내 결제되지 않으면 미수로 넘기는데, 기준이 정해지지 않아(D-10) 지금은 비활성입니다.

끝나면 결제 확정과 운행 종료가 둘 다 확인되면 운행완료가 됩니다(D-09).

누가 누구에게

  2. 판정하면 게스트 환불과 기사 정산 조정이 어떻게 되는지 미리 봅니다. 판정 저장은 정책 결정 전(D-08b)이라 비활성입니다.
  3. 미수는 유형을 자동으로 나누지 않고 '미분류'로 받습니다. 기사 현장 수금 · 손실 처리는 결정 전입니다.

끝나면 판정과 조정이 기록되거나, 미수가 회수됩니다.

문제 — 경보가 너무 늦을 수 있다

지금 경보는 도착 [3]시간 전인데, 중국발 인천행 비행은 대략 1.5~3시간입니다. 그러면 경보 시점은 게스트 출발 1.5시간 전 ~ 출발 시각 사이이고, 비행이 길거나 출발이 당겨지면 이미 기내입니다. 게스트는 공항 수속 · 탑승 중이라 연락이 닿아도 다른 수단을 찾을 시간이 거의 없습니다(덱 5장 "사후 수습 불가"). 아래 그림은 비행 2시간 30분 예시(경보가 출발 30분 전)이며 축척은 임의입니다.

제안 1 — 경보를 두 단계로

경보시점운영자가 할 일
1차 (신설 제안)게스트 출발 전 [n]시간, 예: T-[24]h 점검 때 미배정배정에 집중. 끝내 안 되면 게스트가 출발하기 전에 상황을 알리고 환불 · 대안을 안내
2차 (지금 기준)도착 T-[3]h 미배정마지막 방어선. 관제 '미배차 위험' 필터 → 후보 기사 전화 → 강제배차

제안 2 — 게스트 출발 시각 확보

지금 연동은 도착편 조회뿐이라 출발 시각을 알 수 없습니다. 둘 중 하나를 정해야 1차 경보를 계산할 수 있습니다. ① 예약할 때 출발 공항 · 출발 시각을 함께 받는다 ② 출발편 정보도 조회한다(연동 추가 필요).

제안 3 — 경보 때 쓸 수 있는 수단 늘리기

수단지금쓰려면
강제배차있음 — 01 관제 · 도착 타임라인 + 배정 배정 패널, 11 관제 · 기사 반납 → 재배정—
기사 추가 보상덱에 "우선예약요금 전액 기사 배분"만 있고, 운영자가 급한 콜에 붙이는 수단인지 정의 없음금전 정책 결정(누가 부담 · 금액 · 적용 조건)
제휴 운영사로 넘기기벤치마킹 아이디어 — 온보딩 덱에 없음. 덱은 기사 풀 확보를 근본 방어로 둠 — 18 [벤치마킹 아이디어] 제휴 운영사채택 여부 결정 · 계약

제안 4 — 경보를 기사 모집으로 되돌리기

덱의 결론대로 근본 방어는 기사 풀 확보입니다. 미배차 위험이 뜬 날짜 · 시간대 · 터미널 · 목적지를 월간 검토에서 모아, 기사 모집과 근무 요청에 반영합니다(월간 지표 정의는 공백 G-05).
